# M2.1 — Shared Knowledge / Governed Decisions

**Status:** Implemented and acceptance-tested at local in-process API level. This is a component of the planned Shared Brain, **not** a production multi-agent service.

## Goal and scope

Provide a durable, project-scoped, explicitly governed set of architectural/project decisions. Agents may propose decisions; a local operator reviews and explicitly accepts or rejects them. Other agents receive only **accepted, current** decisions in the default knowledge feed. Original proposed text, reasoning, provenance, author, reviewer, and event references remain accessible under authorization.

This milestone intentionally excludes automatic semantic memory, context snapshot transfer, agent session access, embeddings, vector search, file crawling, MCP transport, remote agent execution, web UI and automated enforcement of decisions in provider prompts.

## Logical state machine

- `proposed -> accepted | rejected`
- `accepted -> superseded` only when a **new, separately proposed decision** referencing the accepted predecessor is itself accepted.
- `rejected`, `superseded` are terminal states.
- No content edits after proposal; changes require a new decision and explicit supersession.
- A decision proposal can be created by an agent or the operator; **only the operator role** can accept or reject. Because M1 only has one operator, a proposal entered by that operator can also be approved by that operator; this is **not** an independent second-person approval.

## Domain methods

| Method | Authorization | Key semantics |
|---|---|---|
| `propose_decision(session_token, statement, rationale, source_refs, request_key, supersedes_decision_id=None)` | Active project session | Immutable draft; 1–8 ordered sources; idempotency keyed by project and stable agent principal |
| `decide_decision(session_token, decision_id, expected_version, outcome, reason, request_key)` | Operator | Only pending proposal, outcome `accepted` or `rejected`; monotonic version; atomic supersession + events |
| `get_decision(session_token, decision_id)` | Operator, author for own private drafts, otherwise authenticated project agent for accepted/superseded | Full statement/rationale, state, author/reviewer, source refs and audit event references |
| `list_decisions(session_token, status='accepted', after_seq=0, limit=100)` | Project session; operator for `proposed`, `rejected`, `all` | Page in stable insertion sequence; filter state; `has_more` and `next_cursor` |
| `knowledge_brief(session_token, limit=20)` | Project session | **Newest active accepted** decisions, max 50 entries; only 320-byte statement previews and references; `preview_truncated` and `has_more` exposed |

A brief is an **index, not a source of complete instructions**. When `preview_truncated=true`, consumers must fetch `get_decision` before applying that decision. For complex decisions, use `get_decision` regardless of preview length to retrieve rationale and provenance.

## Provenance

A proposal requires at least one source reference. Supported kinds:

- `task`: existing task in the current project
- `message`: message in project, only if proposer is its sender/recipient or the operator. The reference does not include the message body.
- `evidence`: existing evidence linked to a task in the current project
- `decision`: already accepted/superseded decision in the current project
- `external`: syntactically constrained HTTPS URL **only**, never fetched or independently verified

Source references are immutable and persist through acceptance/supersession. External URLs are explicitly marked as unverified. Internal reference validation checks existence and project membership; it does **not** verify claim truth, run tests, inspect code, or establish that any linked evidence is genuine.

Accepted decisions expose their source *identifiers* to project agents. In particular an operator may approve a decision citing a private message, thereby sharing that message's **ID**, not body. Operators should review such citations for sensitivity before approval. The future broker must enforce data exposure boundaries.

## Consistency, security, storage

- Schema version increments **2 -> 3**; v2 migration is transactionally applied and the old migration log must contain both v1 and v2 records. Legacy unversioned v0 data is supported after validating its original tables. Unknown/missing versions or partial knowledge schema are rejected, not silently repaired.
- Acceptance of a successor, predecessor supersession, and both audit events share one SQLite `BEGIN IMMEDIATE` transaction. If it fails before commit, the entire change is rolled back.
- Only one successor can supersede a predecessor: two racing approvals cannot both succeed.
- Full decisions carry `proposed_event_id`, `decision_event_id`, and predecessor `superseded_event_id` where applicable.
- Revoked/expired/disabled agent sessions are refused by the same `Workspace._actor` check used in M1.
- The domain API is **not** a security boundary against processes that can read or write the SQLite file directly; the authenticated broker remains a requirement before real agent attachment.
- All persisted decision content is plaintext. No automatic redaction or malware/link fetching occurs. Agents and operators must avoid entering secrets or confidential transcript content.

## M2.1 acceptance gate

This phase is ready as a **local prototype** when all earlier M1 tests still pass and the new tests verify: drafts are non-authoritative; operator-only approval; source ownership and project isolation; immutable provenance; version, idempotency and atomic supersession; private draft visibility; compact newest-first brief; and migration compatibility with an **actual M1.3 database file**.

M2.2 will add separate sourced observation/memory records (not auto-promoted to decisions) and bounded search. M2.3 will add sanitized context snapshots and explicit handoff retrieval. M3 adds an authenticated broker and MCP clients. No production security clearance or independent reviewer sign-off is claimed here.
