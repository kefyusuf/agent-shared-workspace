# M1.3 — Recovery & Security Hardening

**Status:** Implemented/tested for the **in-process local Python domain API**. Not ready to connect untrusted processes, enable MCP, or expose a web listener.

## Scope and non-goals

M1.3 addresses session invalidation, principal offboarding, one-shot agent credential rotation, orphan lease recovery, storage schema tracking, and crash-atomic state changes. It does not introduce adapters, HTTP, UI, knowledge graph, content extraction, agent waking, automatic CI attestation, or operator credential recovery.

## New methods

| Method | Caller | Contract |
| --- | --- | --- |
| `schema_version()` | Local application | Return SQLite `user_version` (currently 2). |
| `session_info(token)` | Valid session | Only the current session's ID and timestamps; no secret returned. |
| `close_session(token)` | Session owner | Revoke the calling session and release its active tasks atomically. Subsequent calls are unauthenticated. |
| `revoke_session(operator_token, session_id, request_key, reason)` | Operator | Revoke a specified project session and release its tasks in one transaction. Idempotent for same operator request key/payload while the operator is authenticated. |
| `disable_agent(operator_token, agent_id, request_key, reason)` | Operator | Disable agent principal, revoke every non-revoked session and release related active tasks. Leave history, evidence, mailbox and reviews intact. |
| `rotate_agent_credential(operator_token, agent_id)` | Operator | Return a fresh credential **once**, revoke old sessions and rotate stored credential hash. Not replayable; a retry performs another rotation. Credential is **not** cached in idempotency storage. |
| `recover_abandoned_tasks(operator_token, request_key)` | Operator | Recover up to 100 `InProgress` tasks with expired lease, expired/revoked session, disabled principal, or missing lease. Each becomes `Ready`; version increments; lease cleared; audit recorded. Run with a new request key to process further batches. |

## State and fencing guarantees

- Releasing a lease and revoking a token are a single `BEGIN IMMEDIATE` transaction, with the corresponding audit records. A simulated exception rolls back both.
- The old task fence cannot be reused from a new session even before a subsequent claim, because session ID and lease holder must match. A new claim increments the fence.
- Revoking one session does not implicitly disable its principal or revoke other sessions. Disabling an agent revokes **all** its sessions.
- A valid, non-expired lease remains untouched by normal recovery. The operator must explicitly revoke a session to force immediate release.
- The recovery operation is **manual** and local. No background scheduler, process monitor, or time synchronization authority is provided.
- Review and evidence history remains intact. Recovered work returns to `Ready`, never `Done`, and its prior evidence cannot be adopted into a new lease without a fresh submission.

## Database compatibility

- New databases are initialized atomically with schema version `2` and migration ledger versions `1`, `2`.
- Existing M1.2 databases normally have SQLite `user_version=0` and the complete M1.2 table set. M1.3 checks required tables/columns, performs SQLite integrity and FK checks, and adds migration tracking **without modifying existing domain records**.
- Unknown newer versions and partial/unrecognized legacy schemas are rejected as `UNSUPPORTED_SCHEMA` rather than silently overwritten.
- Schema version `2` validates the baseline schema and migration record at startup. Migrations are guarded by `BEGIN IMMEDIATE`; startup migrations are not intended as a substitute for a backup.
- On POSIX, the database file is created with `0600` before SQLite opens it; new parent directories are `0700`. Symlink DB paths are rejected. Existing directory ownership and hostile same-UID processes are **not** secured by this.

## Authorization and operational boundaries

- `operator` is a privileged local principal. Only the operator can disable an agent, revoke another session, rotate an agent credential, or recover abandoned tasks.
- A disabled agent cannot create sessions; a revoked session cannot read state, mutate state, or replay previously successful idempotency requests.
- Operator secret rotation/recovery is **not implemented**. Treat the operator credential as a bootstrap root of trust; if lost, use a verified offline backup/recovery process rather than editing SQLite by hand.
- Credentials and session tokens are held as SHA-256 hashes in SQLite; returned raw credentials must be stored securely by the operator. High-entropy random values reduce offline guessing exposure but do not provide confidentiality against malware that observes tokens in process memory.
- Workspace data (message text, review summaries, task descriptions) remains plaintext in SQLite; no field-level encryption or secret redaction has been implemented.
- Crucial boundary: a separate local authenticated broker running under a distinct OS account and owning the DB is **still required** before connecting agents that are not fully trusted. Direct SQLite access bypasses the Python API's authorization checks.
- Adapter operations must never expose `bootstrap`, the fault injector, raw SQLite paths, or raw credential rotation results to untrusted agent tools without an explicit human approval channel.

## Crash and restart behavior

Transaction exceptions roll back before the connection closes, and committed events survive subsequent API process restarts. The tests include injected failures during session retirement and recovery, plus all existing M1.2 review-approval rollback scenarios. These tests are not equivalent to power-loss, filesystem corruption or cross-host crash recovery testing. Database backups should include the WAL state (use SQLite online backup), and restore testing remains an explicit M4 prerequisite.
