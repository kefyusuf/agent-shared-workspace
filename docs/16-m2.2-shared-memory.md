# M2.2 — Sourced Shared Memory and Bounded Retrieval

**State:** Acceptance-tested local, in-process domain API. **Not a production service or an actual MCP agent connection.**

## Purpose and boundaries

The Shared Brain stores operator-approved architectural/project decisions (M2.1). Shared Memory stores **agent-reported observations, findings, failed attempts and lessons**; memory is *not approved knowledge* and **never automatically becomes a Brain decision**. An agent can propose a separate decision by citing appropriate sources and following the M2.1 operator approval gate.

M2.2 does not add vector embeddings, RAG, native conversation/session reads, arbitrary repository crawling, model execution, HTTP endpoints, background jobs, data redaction, source verification, or a web Kanban. Retrieval is **keyword-based FTS5**, not semantic or similarity search.

## Data records

`memory_entries` stores an immutable body and title, kind, project, author, optional task, source reference ownership, optional expiration, event IDs, and lifecycle fields. `memory_sources` provides 1–8 immutable source references. `memory_fts` is a SQLite FTS5 index on title and content (`unicode61`). No additional runtime dependencies are needed for Python builds whose SQLite includes FTS5.

Memory kinds: `observation`, `finding`, `failed_attempt`, `lesson`.

A memory's verification status is **`agent_reported`**. This is not an assertion of factual correctness. A referenced evidence ID, source URL, or passing test report is not itself verified by M2.2.

## State and freshness

`active -> superseded` on a new authorized replacement; `active -> retracted` by the author or operator. A `retracted` record cannot be restored. Superseded/retracted records are never returned by default search. Expiration is a derived state (`effective_status='expired'`, `is_stale=true`) without a background timer. Expired records are hidden from ordinary search, and `get_memory` permits historical reads only by the author or operator. Superseded records can still be read by project agents with `is_stale=true` for audit/provenance.

Correction/replacement needs a new record. Original memory body and sources are immutable. Only the author or operator may retract or supersede a memory. Because expiry is derived at read time, no `memory_changes` event is emitted when a TTL elapses: clients must re-query or compare `expires_at` with current time. Expiry is optional and bounded (`ttl_seconds`: 60–31,536,000). If no TTL is supplied, a record remains active until superseded or retracted; this does **not** imply accuracy or current validity.

## Domain API

| Method | Contract |
|---|---|
| `record_memory(session, kind, title, content, source_refs, request_key, task_id=None, supersedes_memory_id=None, ttl_seconds=None)` | Authenticated project writer; 1–8 valid sources; 256-byte title and 16-KiB content bounds; atomic append/FTS/event and optional supersession; principal-scoped idempotency |
| `get_memory(session, memory_id)` | Authorized project full record with author, age/expiry, source refs, provenance and `is_stale`; retracted or expired content hidden from other agents |
| `search_memories(session, query=None, kind=None, before_seq=None, limit=20)` | Active and non-expired only; literal-token AND FTS5 when query supplied; newest-first bounded previews (title <=160 bytes, body <=320 bytes); stable before-sequence cursor; `has_more` |
| `retract_memory(session, memory_id, reason, request_key)` | Author/operator only, idempotent request, audit trail |
| `memory_changes(session, after_event_id=0, limit=100)` | Project-scoped incremental event metadata (`recorded`, `superseded`, `retracted`); ascending event cursor; no body in stream |

Query text is restricted to 512 UTF-8 bytes and at most 12 literal word tokens; operators and punctuation are not passed into FTS5 as executable query syntax. An empty/punctuation-only query is invalid. Phrase relevance/ranking, spelling correction, stemming, and natural-language semantics are outside scope. Search cursors paginate newest-first by insertion sequence, **not** relevance score. Repeated use with a saved cursor avoids re-reading old active records, but query matches that change state between pages can disappear; this is expected.

## Source authorization and sensitivity

Sources follow M2.1 validation: `task`, `message`, `evidence`, accepted/superseded `decision`, or syntactically constrained **unfetched** HTTPS URL. Internal sources must exist in the project. A non-operator may cite only messages in which the agent is sender or recipient. Other agents can read the shared memory **title/body**, but a private message reference is omitted from `get_memory` when that reader cannot access the underlying message, and `hidden_source_count` reports only a count. Message body is never joined into the memory record. Operator can see source identifiers.

**Important:** An agent can still manually write sensitive/private information into the shared memory title or body. There is **no automated DLP or sanitization**. The first real-agent broker must restrict what may be written, apply access controls and avoid sharing raw transcripts or credentials. Do not expose direct SQLite access to untrusted agents. Stored data and the FTS index remain plaintext.

## Integrity, migration, and limitations

- All mutations and audit/idempotency writes use `BEGIN IMMEDIATE`; concurrent replacements have one winner. A test failpoint exercises an atomic rollback across the record, FTS index, predecessor invalidation, and event log.
- `PRAGMA user_version` moves **3 -> 4**. A v3 M2.1 database is migrated in a transaction; original tasks, messages, sessions, knowledge decisions and audit data remain. Versions 0 and 2 follow the existing earlier migration chain. Unknown/future and incomplete schemas are rejected; partially present memory tables cause an error rather than silent repair.
- FTS5 is checked by actual search tests. No automated FTS repair/reindex, backups, encryption, transactional multi-machine coordination, CI provenance attestation, or production authorization boundary exists yet.
- `memory_changes` only reports events. Clients must explicitly request current records and should treat reported content as unverified observations, not system instructions.

## M2.2 acceptance gate and next step

The gate requires M1/M2.1 regressions passing, new memory tests covering sharing, provenance, private message references, full-text retrieval, invalid query syntax, pagination, expiry, corrections, concurrent replacement, revocation, crash rollback, persistence, and real v3 -> v4 migration.

**Next: M2.3 Context Gateway.** Structured, selective context snapshots, bounded handoffs and scoped context retrieval. The external MCP/broker and Kanban remain M3.
