# M1.2 — Review & Evidence Gate Implementation Report

**Status:** Verified local domain API prototype, not production-ready. 2026-11-01.
**Scope:** Evidence records and `InProgress -> Review -> Done` with explicit operator attestation.
**Out of scope:** real CI execution, artifact integrity verification, MCP, provider sessions, shared Brain/Memory, visual Kanban, service security boundary.

## Behavior and invariants

1. Only an enrolled **agent principal** can claim a Ready task. An operator cannot claim tasks in this pilot, preventing accidental self-review deadlocks.
2. Evidence is an immutable reference (`test_report`, `commit`, `diff`, or `manual_check`), accompanied by a reported result and explanatory note. Every evidence reference is bound to the **specific active lease ID, principal and task**. An earlier lease's evidence is not attachable to a new review submission.
3. Adding evidence is lease-, fence- and version-protected; it increments the task version and commits an audit event atomically.
4. Submitting for review requires at least one evidence reference from the current lease plus a non-empty handoff summary. The lease is released; the author and review submission are stored permanently. This handoff summary is **not** the M2 ContextSnapshot feature.
5. Only the human operator can mark submitted evidence as `verified` or `rejected`. In M1.2, the method is explicitly recorded as `operator_attestation`: it records an operator's manual claim of inspection, **not automatic authentication** of the CI run, commit, file, logs or test result.
6. The operator can approve a pending review only after **every attached evidence reference is verified**, at least one test report is present, and **every test report says `passed`**. Merely verified failed-test reports do not permit Done. Approval stores a rationale and rejects reviewer identity equal to author identity.
7. The author/another agent cannot verify evidence or approve their own review. Direct `finish_task` remains fail-closed (`REVIEW_REQUIRED`). No `review_required=false` bypass is implemented.
8. On rejected/incomplete work, the operator uses `request_changes` to transition **Review -> Ready**, not directly to InProgress. A new fenced lease is required before work can resume. This tightens M0's conceptual Review -> InProgress transition to avoid a work-in-progress task lacking a valid owner. Previous review attempts and evidence remain auditable.
9. Every transition validates `expected_version`. All domain writes and audit events share one SQLite transaction. Idempotency keys are project-and-principal scoped, survive session reconnects, and reject reused keys with different arguments.
10. Untrusted context text, test reports and external paths are **never executed or opened** by the coordination core. Secret screening and validated context-source file access remain M2 work.

## Minimal review contract

| API method | Principal | Preconditions | Effect |
|---|---|---|---|
| `add_evidence` | Lease owner agent | InProgress; active lease; matching fence and version | Store submitted source reference; increment version; event |
| `submit_for_review` | Lease owner agent | At least one unbound evidence from current lease | Attach evidence, store handoff, release lease, status Review |
| `get_review` | Project member | Task and review exist | Read latest submission and its associated evidence |
| `verify_evidence` | Operator | Review pending; evidence submitted; expected version matches | Operator attestation; evidence verified/rejected; increment version |
| `approve_review` | Operator, not author | Review pending; all evidence verified; all test reports passed; >=1 test report | Review approved; task Done; event |
| `request_changes` | Operator, not author | Review pending; matching version | Mark review changes_requested; task Ready; event |

All mutations include a non-empty idempotency request key. `approve_review` never reads source artifacts itself; an external verifier adapter, check fingerprints and signed attestations are future work.

## Open risks and next decisions

- Direct SQLite access is **not a security boundary** against an adversarial process with filesystem access. Authenticate and isolate a local service before real MCP clients connect.
- Evidence references and test result labels are arbitrary strings. `operator_attestation` can be incorrect or dishonest and is not independently verified by the system. Automated check adapters, report digests, signed attestations, provenance, evidence policy waivers and cryptographic artifact verification are unimplemented.
- Credentials, session revocation, principal disable, operator rotation/recovery, backups, quotas and data retention remain incomplete. Plaintext handoff/reference data must not contain secrets.
- At present there is no per-resource fine-grained read permission for evidence within the same project. A project member can read current task review and evidence references.
- The core is one project per database and one host. SQLite DDL uses additive `CREATE TABLE IF NOT EXISTS` changes for the prototype; no schema migration/versioning mechanism or rollback tooling yet.
- The M0 gate still lacks human operator sign-off. No Git commit/push or actual provider client testing is claimed.

**Next bounded milestone:** M1.3 — lifecycle hardening (session revocation and agent disable, restart recovery runbook, schema migration policy, isolation requirements), **then M2** context/knowledge. Do not add MCP/UI yet.
