# M3.1 — Authenticated Local Broker

**Status:** Local HTTP broker verified with black-box tests. NOT an MCP implementation, hardened sandbox, encrypted transport or production-ready service.

## Purpose and interface

The M2.3 domain `Workspace` state remains authoritative. `agent_workspace.broker` exposes a small allowlisted subset of its operations via JSON over HTTP bound exclusively to IPv4 `127.0.0.1`. Agents never need to open the SQLite file when using the broker. The server does not run any agent or read project source files.

* `GET /v1/health` returns only `{"ok":true,"status":"healthy"}` and no project data.
* `POST /v1/session` accepts `{"credential":"..."}` and returns a time-limited bearer session from the existing domain implementation.
* `POST /v1/call` takes `Authorization: Bearer <session_token>` and `{"operation":"list_tasks","arguments":{}}` (or another allowlisted operation). The session is checked before operation dispatch. Each underlying call rechecks its own role and object permissions.

The allowed operations are listed explicitly in `broker.py`. There is no `eval`, dynamic user-selectable attribute, SQL route, arbitrary path accessor, bootstrap route, direct `enroll_agent` route, CI verification bypass or direct `finish_task` call. Existing domain idempotency, fencing, audit and review rules remain authoritative.

## Security properties tested

1. Bound only to `127.0.0.1`; wildcard and remote binds are rejected.
2. JSON requests limited to 32,768 bytes with exact content type and content length; invalid and duplicate fields rejected.
3. Host allowlist limits DNS-rebinding requests; all browser `Origin` requests denied. No CORS permission is provided.
4. Bearer required on every RPC; revoked/invalid tokens fail even for unknown operations.
5. Domain role and object permissions prevent unauthorized task mutation and another agent's private message reads.
6. Errors never return raw credentials, request bodies or exception traces. Built-in access logs are suppressed. Responses use `Cache-Control: no-store`.
7. Concurrent HTTP task-claim attempts retain the existing atomic owner invariant and domain idempotency.

## Threat model and limitations

This is a **transport boundary**, not an OS sandbox. An agent process running under the **same OS user** as the broker may bypass application authorization if it can read/write the SQLite database directly. POSIX DB mode 0600 prevents other users by default, but does not isolate processes of the same user. For stronger isolation the broker must run under a distinct restricted OS identity and the database directory must be protected by OS permissions before connecting untrusted agent processes. Windows ACL provisioning is not implemented. Loopback HTTP is not TLS and localhost software can potentially intercept or interact with it. Auth failures are not rate limited; credentials are high entropy. Storing plaintext summaries and accepting agent-generated text remains subject to secret disclosure and prompt-injection risks. Broker request authentication does not make referenced evidence trustworthy.

`Origin` denial is intentional and will require a deliberate, authenticated CSRF-safe design when the browser Kanban phase is implemented. This broker is not an Internet-facing API, not ready for remote access, not native session sharing, and not MCP. No provider-specific compatibility is claimed.

## Operator setup

Start a new workspace using a project directory already on disk (do not commit `.local/`):

```sh
PYTHONPATH=src python -m agent_workspace.broker init --db .local/workspace.db --name "Sample Project" --root .
PYTHONPATH=src python -m agent_workspace.broker serve --db .local/workspace.db --port 8765
```

The initial command outputs the one-time operator credential to the trusted local terminal. Do not paste it into project files, commit messages, browser URLs, command arguments or chat. Store it in an appropriate local secret manager. `serve` refuses to silently bootstrap a missing database. Agent enrollment remains a trusted operator-only **domain** operation in M3.1 and will gain a controlled operator interface in a subsequent stage.

Example using a short-lived token obtained via session login:

```sh
curl --fail-with-body -H 'Content-Type: application/json' -d '{"credential":"REPLACE_WITH_CREDENTIAL"}' http://127.0.0.1:8765/v1/session
curl --fail-with-body -H 'Content-Type: application/json' -H 'Authorization: Bearer REPLACE_WITH_SESSION_TOKEN' -d '{"operation":"list_tasks","arguments":{}}' http://127.0.0.1:8765/v1/call
```

**Avoid using literal credentials in shell history**, including copy-pasting these examples. Prefer an HTTP client that can read secrets interactively or from a local secret manager. These request examples are documentation only and use placeholders.

## M3.1 → M3.2 gate

Pass the full M2.3 regression suite and broker HTTP tests. Independently review the broker route allowlist and deployment permissions. Ensure operator accepts the limits of same-user access to SQLite. M3.2 can then add MCP stdio adapters using broker credentials without expanding the underlying data schema.
