# M2.3 — Permissioned Context Gateway and Explicit Handoffs

**State:** Acceptance-tested local, in-process Python domain API. Not production-ready; no MCP, agent runner, session replay, web Kanban or transport security boundary.

## Architecture and non-goals

A context snapshot is an **immutable, structured, agent-reported task checkpoint** with a summary, next steps, optional blockers, up to 16 relative changed-path *labels* (no file read or existence check), and 1–8 typed source references. It is not a provider transcript. Snapshots are bound to a task's active lease ID, fencing token, writer session, and task version at publish time. Publishing does not change the task version or release a lease.

A handoff is an **explicit per-snapshot, per-recipient read grant and action request**. It does not start/notify another provider session, send an ordinary mailbox message, claim/release/reassign a task, or imply a finished review. Inbox polling is required. The recipient can continue work after the current holder releases the lease and the recipient atomically claims the task.

The user-visible *Shared Brain* remains M2.1 operator-governed. *Shared Memory* remains M2.2 agent-reported. Context links to them by stable ID, **not by copying their full texts** into a new prompt or implicitly promoting unreviewed memory to approved decision.

## API and contracts

| Method | Contract |
|---|---|
| `publish_context(session, task_id, expected_version, fence_token, summary, next_steps, source_refs, request_key, changed_paths=None, blockers=None)` | Agent must own a live active task lease; immutable snapshot + source refs + audit event in one transaction, principal-scoped idempotency |
| `send_handoff(session, snapshot_id, recipient_agent_id, action_required, request_key)` | Snapshot author must still hold **that same** live lease; recipient must be enabled project agent and distinct; one grant per snapshot/recipient; transactional audit/event |
| `get_context(session, snapshot_id)` | Permissioned full structured snapshot. Sources dynamically filter private messages and stale memories/decisions; no joined source bodies |
| `list_task_contexts(session, task_id, before_seq=None, limit=20)` | Newest-first, permissioned 256-byte summary previews; pagination anchored on insertion sequence |
| `handoff_inbox(session, after_seq=0, limit=20)` | Per-recipient immutable handoff notifications; ascending sequence cursor, capped page |
| `context_changes(session, after_event_id=0, limit=100)` | Project-scoped, permission-filtered event metadata, no summary, action body, message text or source text |

All reads first validate the active session and project; a disabled agent or revoked token cannot read. A snapshot is visible to its author, operator, explicitly named handoff recipient, **or the current live session holding that task lease**. No generic "read every other agent's context" permission exists. Historical authors retain access to their own snapshots even after a handoff, provided they have a valid session.

### Source references

Allowed types: `task`, `message`, `evidence`, `decision`, `memory`, `external`.

- The task source must be the snapshot's task. Evidence sources must belong to this task.
- `decision` must be *accepted* at publish time; `memory` must be active, unexpired and either task-local or project-global.
- The author can cite a message only if they are its sender/recipient. The recipient of a handoff **cannot** see a private message source ID unless they independently have message access. Unreadable source IDs are removed from `get_context`, and `hidden_source_count` increases. No message body is joined.
- Source refs to later superseded decisions or expired/retracted memories are omitted on later reads and reflected via `stale_source_count`; snapshots themselves remain immutable.
- External HTTPS references are syntactically validated, not fetched or verified. A memory reference is **not** evidence of correctness, and operator evidence verification may itself be manual attestation.

### Size and paging rules

Snapshot: summary <= 4096 UTF-8 bytes; next steps <= 2048; optional blockers <= 2048; 0–16 relative paths, each <= 256; 1–8 source references. Path metadata rejects absolute paths, `..`, `.`, backslashes, duplicate entries, control bytes and drive-qualified paths. Paths are not opened or normalized to files. Handoff action <= 2048 UTF-8 bytes. Summary list previews <= 256 UTF-8 bytes. List/inbox/event pages have max limit 100.

There is no tokenizer-specific budget or automatic context concatenation. The proposed consumer should request a short task list first, then choose one specific context and optionally dereference selected source records. This minimizes unrequested transfer but does **not** prove token savings. Future broker/tool adapters can enforce a per-request budget once real measurement is available.

### Write atomicity and schema

- `BEGIN IMMEDIATE` protects snapshot + refs + event + idempotency in one transaction. Handoffs and grants are similarly atomic. Failure injection tests verify rollback of both operations.
- Schema migration: SQLite `PRAGMA user_version = 5`, records v1–v5 in `schema_migrations`; validated v4 -> v5 upgrade uses version 4 tables and checks migration history. Unknown/future, incomplete and partially created context tables are rejected without silent repair.
- Context is persisted in `context_snapshots`, `context_sources`, `context_handoffs`. No new external dependencies, cron tasks, network listeners or indexing infrastructure.

## Security limitations

**This is not an authorization boundary against a process that can access the SQLite file directly.** The M3 authenticated broker must separate untrusted agent processes and prevent direct database/file access. Snapshot summary, next steps, blocker text, changed paths, and the handoff action are **written by agents** and may themselves contain secrets, private material or malicious instructions. No DLP, prompt-injection defenses, data classification, token counting, encryption-at-rest, OS-level isolation or content verification has been implemented. Only *source reference IDs* have access filtering. Consumers must treat the entire snapshot as untrusted data rather than instructions.

Handoff grants persist for the named principal across their reconnects until future revocation controls are introduced. Disabling a principal denies access; merely revoking one session does not revoke a principal-level grant when that principal opens a valid new session. There is no explicit handoff-grant withdrawal in M2.3. Avoid publishing sensitive content and use this domain API only with trusted local simulations.

## Acceptance and pilot gate

All 114 prior regression tests remain passing, plus M2.3 tests for leases/fencing, authorization isolation, direct handoffs, pagination, revocation, immutable snapshots, path validation, stale sources, concurrency, rollback, unsupported schema, and real old-version migration. The new `examples/context_handoff.py` illustrates a no-provider simulation.

**Next milestone (M3):** repository bootstrap and TDD-driven authenticated local broker, small MCP adapter and minimal Kanban UI. Repo/CI becomes valuable before this phase. M3 must include security testing that explicitly blocks untrusted direct SQLite access, plus a real Codex/Claude Code pilot before claiming interoperability or token savings.
