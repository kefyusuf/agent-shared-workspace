# M3.2.1 — Real Coding-Agent Compatibility Gate

**Status: ready to run on the operator's Windows machine; not yet executed with genuine Codex or Claude Code CLI processes.** This document does not assert provider verification, successful host behavior, or OS isolation.

## Scope

This small follow-up to M3.2 introduces:

- best-effort broker session cleanup when an MCP stdio subprocess ends normally (active task leases are released transactionally);
- a credential-redacting `scripts/host_preflight.py` with only an ephemeral session side effect that probes a live local broker and MCP protocol subprocess;
- a trusted `operator_cli create-task` command for seeding one explicit pilot task;
- `scripts/start_agent_windows.ps1` to launch *one* real provider CLI at a time with a masked credential prompt and per-process environment;
- a manual, reviewable compatibility-evidence checklist.

No MCP tool, websocket, provider session API, Kanban, push notification or native conversation-history access is added. The agent/provider identity and task permissions are still enforced in the broker/domain API. The operator CLI still needs direct access to the SQLite file; the MCP adapter does not.

## Prerequisites

- Windows with Python 3.11+ (`py`), recent `codex` CLI and `claude` CLI installed, and PowerShell.
- A **disposable local repository checkout** and local test workspace without confidential user/project data.
- A trusted terminal for the operator; operator credential must never enter an MCP client or be committed.
- `feat/m3-2-1-compatibility-gate` checkout (dependent on draft PR #2; not merged).
- Both clients and the broker run on the *same host* and see `127.0.0.1:8765`. An IDE/remote container may NOT share the host network.

**Important trust boundary:** Running untrusted agents as the same OS user as the SQLite DB owner can bypass broker authorization. The following is only a controlled compatibility pilot; do not grant untrusted agents sensitive repositories or secrets. Separate OS accounts and file ACLs are a separate, uncompleted security gate.

## 1. First-time trusted operator setup

PowerShell in the checked-out repo:

```powershell
$env:PYTHONPATH = (Resolve-Path .\src).Path
py -m unittest discover -s tests -v
py -m agent_workspace.broker init --db .local/workspace.db --name "Compatibility Pilot" --root .
```

Run `init` only once. It prints the operator credential once; save it securely and do **not** paste it into a chat. Enroll two *distinct* agents, capturing the returned agent IDs and credentials privately:

```powershell
py -m agent_workspace.operator_cli enroll --db .local/workspace.db --name codex --provider codex
py -m agent_workspace.operator_cli enroll --db .local/workspace.db --name claude --provider claude
py -m agent_workspace.operator_cli create-task --db .local/workspace.db --title "MCP cross-agent handoff pilot" --acceptance-criteria "Agent A publishes a sourced snapshot; Agent B reads it after handoff and claims the released task" --request-key "m3-2-1-pilot-task"
```

All three trusted CLI invocations prompt for the operator credential without putting it in the command line. Record only the **task ID**, not credentials, in your verification notes.

## 2. Start the broker

Use a separate operator terminal, in the repo:

```powershell
$env:PYTHONPATH = (Resolve-Path .\src).Path
py -m agent_workspace.broker serve --db .local/workspace.db --port 8765
```

Keep the broker running for the manual session.

## 3. Configure both provider clients without storing credentials

### Codex

Add this entry to your local `~/.codex/config.toml` (do not commit it):

```toml
[mcp_servers.agent_workspace]
command = "py"
args = ["-m", "agent_workspace.mcp_stdio"]
env_vars = ["AW_AGENT_CREDENTIAL", "AW_BROKER_PORT", "PYTHONPATH"]
```

Check using `codex mcp list` and, inside Codex, `/mcp`. **Do not use `codex mcp add --env AW_AGENT_CREDENTIAL=<secret>`**, because that can persist the credential in configuration and shell history. Codex forwards the environment variables named in `env_vars` from the Codex process. Relevant reference: <https://learn.chatgpt.com/docs/extend/mcp>.

### Claude Code

From the workspace checkout, register a **local-scope** stdio server with no `--env` arguments:

```powershell
claude mcp add --scope local --transport stdio agent-workspace -- py -m agent_workspace.mcp_stdio
```

Inspect via `claude mcp list`, then use `/mcp` in Claude Code. The server process must inherit `PYTHONPATH`, `AW_BROKER_PORT`, and its *own* `AW_AGENT_CREDENTIAL` from the launching terminal. If a local Claude Code version does not forward the required environment, stop: do not fix this by embedding a credential in a project-wide `.mcp.json`. See <https://code.claude.com/docs/en/mcp>.

## 4. Run each agent in a separate terminal

Terminal **A**:

```powershell
.\scripts\start_agent_windows.ps1 -Provider codex -Port 8765
```

Terminal **B**:

```powershell
.\scripts\start_agent_windows.ps1 -Provider claude -Port 8765
```

Each launch masks the credential prompt, runs the preflight without mutating project tasks, messages or context (broker health, `initialize`, 16 tools, `workspace_identity`), and then starts the requested CLI. It does not display credentials or agent session tokens. PowerShell process environment variables remain visible to processes with sufficient OS-level privileges; do not treat this as sandboxing.

The preflight's `real_provider_verified` is deliberately **always false**. It tests our stdio server, not the client software itself. No provider evidence is inferred from a CLI binary existing.

## 5. Manual host integration acceptance tests

Use the real clients' tool interfaces (and inspect actual MCP tool responses, not just agent prose):

1. **Discovery/identity:** Both report `workspace_identity`; their `agent_id`s are distinct and each role is `agent`. Verify `task_list` returns the seeded task from both hosts.
2. **Mailbox privacy:** Codex sends `mail_send` to the Claude ID using a unique request key. Claude sees it with `mail_inbox`. If there is a third agent, it must not read this private message.
3. **Atomic claim:** Codex claims the seeded task using the returned version. Claude's concurrent claim must be rejected with a domain conflict.
4. **Sourced snapshot:** Codex calls `context_publish` while its lease is active using a `task` source ref pointing to the seeded task. Claude initially cannot read it.
5. **Explicit handoff:** Codex calls `context_handoff` for Claude's agent ID. Claude receives the event via `context_inbox`, reads with `context_get`, then Codex releases its task and Claude claims the new Ready version. Old fence must not be reusable.
6. **Graceful shutdown:** Exit both clients normally. Check the seeded task returns to Ready if still leased and that sessions are closed. If a process is killed, task recovery depends on lease expiry instead.
7. **Revocation:** Using the trusted operator/domain control path, revoke a test agent session and confirm its next MCP domain call is denied; no session token or credential appears in the report.
